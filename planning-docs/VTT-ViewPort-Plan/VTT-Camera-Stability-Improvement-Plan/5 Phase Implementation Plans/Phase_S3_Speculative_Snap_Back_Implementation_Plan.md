# Phase S3: Speculative Snap-Back and Momentum Detection
## A comprehensive implementation plan for eliminating the elastic overscroll freeze through EWMA-based stall detection, speculative animation launch, and defense-in-depth race condition prevention

**Fixes:** Bug #1 (elastic offset freezes for 1–2 seconds before snap-back begins)
**Impact:** High. Eliminates the most common and most visible complaint about the camera system.
**Risk:** Medium. Timing-sensitive code with multiple concurrent animation loops requires careful coordination and thorough testing.
**Estimated LOC:** ~200 (EWMA stall detector + speculative snap-back launcher + momentum detection tightening + race condition defenses + `_snapBackElastic` guard)
**Depends on:** Phase S1 (stateful device classification) and Phase S2 (velocity-clamped spring snap-back). S1 ensures trackpad scroll events reach `panBy()` and generate elastic offset. S2 ensures that every call to `_snapBackElastic()` — including the speculative calls this phase introduces — inherits overshoot protection automatically.

## 1. Why this phase comes third {#why-third}

The first two stabilization phases fixed the input routing (S1: fast trackpad scrolls now correctly pan instead of zooming) and the animation output (S2: the spring snap-back never overshoots, regardless of initial velocity). Phase S3 fixes the gap between them: the dead time between the user lifting their fingers and the snap-back animation beginning.

The ordering is critical for a specific reason: Phase S3 introduces a new caller of `_snapBackElastic()`. The speculative snap-back system calls `_snapBackElastic()` *before* the `TrackpadGestureDetector` has formally detected gesture end, whenever the EWMA velocity of elastic offset growth drops below a threshold. If this phase had been implemented before S2, these speculative calls would have passed unclamped velocity to the spring, potentially triggering the overshoot bug in a new and harder-to-reproduce context (the velocity at the moment of speculative trigger is partially decayed, making the overshoot intermittent rather than consistent). With S2 in place, every call to `_snapBackElastic()` — whether from formal gesture end, inertial coast termination, or speculative trigger — passes through the velocity clamp, making overshoot mathematically impossible regardless of the call site.

Phase S3 also depends on S1 for a subtler reason. The speculative snap-back monitors elastic offset growth rate. This monitoring only produces useful data when elastic offset values are generated by actual trackpad pan events hitting the map boundary. Before S1, fast trackpad scrolls were misrouted to `SmoothZoomAnimator.onWheelZoom()`, which zoomed the camera instead of panning it. The camera never reached the boundary, elastic offset was never generated, and the speculative system would have had nothing to monitor. With S1's correct classification, fast scrolls generate elastic offset at the boundary, and the EWMA has real data to work with.

The risk assessment is medium (higher than S1 or S2) because this phase introduces timing-dependent behavior. The EWMA stall detector runs at 60Hz, the speculative snap-back launches and cancels animation frames, and the formal `TrackpadGestureDetector` continues running in parallel with its own timeouts. These concurrent timing systems create race conditions that do not exist in S1 (pure function replacement) or S2 (pure math). The five-layer defense strategy in Section 5 addresses each race condition systematically.

## 2. The philosophical problem: waiting for certainty in a perceptual system {#philosophy}

### Why the freeze exists

The current system follows a conservative sequence. When the user scrolls past the map boundary:

1. The `TrackpadGestureDetector` enters the ACTIVE state and the elastic offset grows as `_feedElasticOverflow()` is called on each wheel event.
2. When the user lifts their fingers, macOS generates synthetic momentum events with decaying deltas. The detector watches for **3 consecutive decaying deltas** after at least **6 events** to transition from ACTIVE to MOMENTUM.
3. Once in MOMENTUM, the detector waits for **100ms of silence** (no more wheel events) to fire `onGestureEnd`.
4. Only when `onGestureEnd` fires does `_snapBackElastic()` begin animating the elastic offset back to zero.

The freeze occurs during steps 2 through 4. The elastic offset is visually frozen at its maximum displacement — the rubber-band is stretched out, the user's fingers have lifted, but nothing is moving. The detection window is conservative by design: 3 decaying deltas plus 100ms silence adds up to roughly 150–250ms of detection latency, and for fast gestures that produce few momentum events, the total latency can stretch to 1–2 seconds.

This sequence treats the visual response (snap-back animation) as a consequence of formal state detection (momentum confirmed → gesture ended → animate). The logic is: "I must be certain the gesture ended before I start the snap-back." This is a correct approach for irreversible actions, but snap-back is not irreversible. It is a `requestAnimationFrame` callback that can be cancelled with `cancelAnimationFrame()` at any time. The cancel cost is one wasted frame — 16 milliseconds of computation that the user never sees.

### The speculative execution paradigm

The insight comes from CPU architecture. Modern processors do not wait for a branch condition to resolve before starting the next instruction. They predict which branch will be taken (based on history, heuristics, or static analysis), start executing instructions along the predicted path, and either commit the results (if the prediction was correct) or flush the pipeline and restart (if it was wrong). The penalty for a correct prediction is zero. The penalty for a wrong prediction is a pipeline flush of a few cycles. The alternative — stalling the pipeline until the branch resolves — wastes cycles on every branch, even the 95%+ that are correctly predicted.

Apple's WWDC 2018 "Designing Fluid Interfaces" talk applied this principle to interaction design. Their iPhone X home indicator gesture does not wait for velocity to stabilize before starting the multitasking animation. Instead, it detects the acceleration spike when your finger decelerates and starts the animation immediately. "The faster you stop, the faster we can detect it." If the prediction is wrong (the user continues the gesture), the animation is smoothly cancelled and the system follows the finger again. The key quote from the talk: "Look for delays everywhere. Everything needs to respond instantly."

Google's RAIL model makes the threshold explicit: visible feedback must appear within 100ms of user action. The current 150–250ms detection latency (and up to 1–2 seconds for edge cases) violates this threshold. The user lifts their fingers, sees the rubber-band frozen in place, and perceives the system as broken.

### The cost asymmetry

The speculative snap-back strategy exploits an extreme asymmetry in error costs:

| Prediction | Outcome | Cost |
|---|---|---|
| Start snap-back, user has stopped | Correct: snap-back completes smoothly | Zero — this is the desired behavior |
| Start snap-back, user is still scrolling | Wrong: cancel animation, resume following input | 1–3 frames of invisible wasted computation (~16–48ms) |
| Wait for certainty, user has stopped | Correct, but late: 150–2000ms of frozen overscroll | Perceptually broken. Violates RAIL 100ms threshold. |
| Wait for certainty, user is still scrolling | Correct: no premature animation | Zero — but this case is rare (usually the user has stopped) |

The expected cost of speculation is near-zero because the misprediction penalty is imperceptible and the correct-prediction benefit is substantial (eliminating the freeze entirely). The expected cost of waiting is high because the freeze is perceptible every time the user scrolls past a boundary.

This is exactly the cost structure that makes branch prediction valuable in CPUs: the misprediction flush is cheap, the stall is expensive, and most predictions are correct. In our case, most frames where the EWMA drops below threshold are genuine gesture ends, making the "prediction" accurate the overwhelming majority of the time.

### The formal detector becomes a confirmation mechanism

After this phase, the `TrackpadGestureDetector` still runs. It still tracks IDLE → ACTIVE → MOMENTUM → IDLE transitions. It still fires `onGestureEnd`. But it no longer gates the visual response. Instead, it serves as a confirmation mechanism for state management:

- It drives `_gestureActive` and `_momentumScrollActive`, which control the rubber-band coefficient in `_feedElasticOverflow()` (0.55 during active scrolling, 0.3 during momentum).
- It fires `onGestureEnd` to update the `GestureStateMachine` (releasing `SCROLL_PAN` and requesting `SNAP_BACK`).
- It provides a cleanup backstop: if the speculative system somehow fails to trigger snap-back (a defensive impossibility, but defense-in-depth demands it), the formal `onGestureEnd` will trigger it as a fallback.

The visual response, the snap-back animation, is driven by the EWMA stall detector on every frame. The formal detector is for bookkeeping; the speculative detector is for responsiveness. This separation of concerns is the core architectural change of Phase S3.

## 3. EWMA stall detection: the math, the constants, and the intuition {#ewma-math}

### What the EWMA computes

The Exponentially Weighted Moving Average (Roberts, 1959) is a recursive low-pass filter defined by:

```
S_t = α · x_t + (1 − α) · S_{t-1}
```

where `x_t` is the current observation (per-frame change in elastic offset magnitude) and `α` is the smoothing factor (0 < α < 1). Higher α responds faster to changes but is more sensitive to noise. Lower α provides more smoothing but introduces more lag.

The EWMA has three properties that make it ideal for stall detection:

**1. Temporal consensus.** A single slow frame contributes only α (20–30%) of its value to the smoothed output. This prevents false positives from timing jitter, rAF scheduling variance, or brief pauses during active scrolling. The EWMA requires sustained low activity to drop below the threshold, which is exactly the behavioral signature of "the user stopped scrolling."

**2. No windowed memory management.** Unlike a simple moving average (which requires storing N samples and managing a circular buffer), the EWMA stores only one number: the current smoothed value. This is elegant, cache-friendly, and requires zero memory allocation in the hot path.

**3. Exponential decay of old observations.** The weight of observation `x_{t-k}` in the current EWMA value is `α · (1-α)^k`. After `k = ln(0.01) / ln(1-α)` frames, an observation contributes less than 1% to the current value. For α = 0.3, this is about 13 frames (217ms at 60Hz). Old momentum events naturally fade from influence without explicit window management.

### Choosing α = 0.3

The effective memory window of the EWMA is `N = 2/α − 1` samples. The half-life (frames for a weight to decay 50%) is `ln(0.5) / ln(1-α)`.

| α | Effective window (frames) | Half-life (frames) | Half-life (ms @ 60Hz) | Detection latency from 5px/frame |
|---|---|---|---|---|
| 0.2 | 9.0 | 3.1 | 52ms | ~172ms |
| **0.3** | **5.7** | **1.94** | **32ms** | **~108ms** |
| 0.4 | 4.0 | 1.36 | 23ms | ~73ms |
| 0.5 | 3.0 | 1.0 | 17ms | ~53ms |

Detection latency is the number of zero-speed frames required for the EWMA to decay from a typical scrolling speed (5 screen pixels per frame) to the stall threshold (0.5 screen pixels per frame). The decay follows `V · (1-α)^n < threshold`, so `n = ln(threshold/V) / ln(1-α)`.

At **α = 0.3**, detection latency is approximately **108ms** (6.5 frames). This is:

- Below the 200ms threshold where users begin to consciously perceive delays
- Within Google's RAIL 100ms response budget when combined with the 16ms frame latency of the first speculative snap-back frame
- Substantially faster than the current 150–2000ms detection window
- Slow enough to avoid false positives during brief pauses in active scrolling (a single slow frame contributes only 30% of its value)

α = 0.4 would give ~73ms detection, which is faster but more susceptible to false positives during natural variations in scroll speed. α = 0.2 would give ~172ms detection, which is safer but slower than necessary (the RAIL budget is 100ms, not 172ms). α = 0.3 is the sweet spot.

### EWMA initialization: the anti-fast-initial-response trick

Roberts' original paper introduced the "Fast Initial Response" (FIR) technique: initialize the EWMA close to the expected observation value so that initial observations have immediate influence. For change-point detection in manufacturing, this reduces time-to-detect for shifts that occur early in the process.

We want the opposite. We want the EWMA to start **high** so that the speculative snap-back does not trigger immediately when elastic offset first becomes nonzero. If we initialized at zero, the first frame of overscroll would have `x_t = some positive value` and `S_0 = 0`, so `S_1 = α · x_t + (1-α) · 0 = α · x_t`. For small α · x_t values, this could be below the stall threshold, triggering a false snap-back on the very first overscroll frame.

Instead, we initialize at **10 screen pixels per frame**, which is well above any reasonable stall threshold. With α = 0.3, the EWMA needs approximately **8.4 frames (140ms)** of sustained zero-speed to decay from 10 to the 0.5 threshold. This 140ms warm-up prevents the system from prematurely snapping back during the first few frames of overscroll, where the rate of change can be noisy as the rubber-band formula establishes its curve.

The formula: from `S_0 = 10`, with zero input, `S_n = 10 · (1-0.3)^n = 10 · 0.7^n`. We need `10 · 0.7^n < 0.5`, so `n > ln(0.05) / ln(0.7) = 8.4 frames`.

### The stall threshold must be in screen pixels

In a zoomable canvas, the same world-space delta produces very different visual movement at different zoom levels. At 10× zoom, a 0.5 world-pixel change is 5 screen pixels of visible movement — clearly not a stall. At 0.1× zoom, a 0.5 world-pixel change is 0.05 screen pixels — invisible, definitely a stall.

The stall threshold must be in **screen pixels per frame** to produce perceptually correct behavior across all zoom levels. The conversion happens at the point where `x_t` is computed:

```javascript
// Correct: screen-space speed
const currentScreenMagnitude = Math.sqrt(
  (this.elasticOffsetX * this.zoom) ** 2 +
  (this.elasticOffsetY * this.zoom) ** 2
);
const delta = Math.abs(currentScreenMagnitude - this._lastElasticScreenMag);
```

This naturally adapts to zoom level without any threshold adjustments. A stall at high zoom is correctly detected when screen-space movement drops below 0.5px, even though the world-space movement might be much smaller.

## 4. How production applications handle the freeze problem {#production-approaches}

### iOS UIScrollView: zero-delay bounce-back via native APIs

UIScrollView has zero perceptible delay between finger-lift and bounce-back because of three architectural advantages the web lacks. First, `UIPanGestureRecognizer.ended` fires synchronously on the main thread the instant the finger lifts, and the animation starts in the same run loop iteration. No async gap. Second, the gesture recognizer directly provides velocity via `velocity(in:)`, eliminating the need for momentum detection. Third, Core Animation's render server runs in a separate process, decoupled from main thread work.

The bounce-back itself is a critically damped spring with response time ~0.4 seconds, stiffness ≈ 246.7, and damping ≈ 31.4 (derived from the WWDC 2018 conversion formulas: `stiffness = (2π/response)²`, `damping = 4π · dampingRatio / response`). The key property: **settling time is roughly constant regardless of displacement**. A 10× increase in offset adds only `~ln(10)/ω_n ≈ 0.15s` to settling time.

JavaScript cannot replicate this. Browsers withhold `NSEventPhase` and `NSEventMomentumPhase`. The W3C proposal (`WheelEvent.isInertialScrolling`, issue #58) has been open since 2015 with no implementation. We must use heuristics, and the speculative approach is the closest we can get to iOS's instant response.

### React Native Animated.decay(): speculative by default

React Native's `Animated.decay()` demonstrates the speculative pattern directly. On gesture end (`onPanResponderRelease`), it takes the last known velocity and immediately begins exponential deceleration with a configurable rate (default 0.997 per frame). If the user touches again mid-decay (`onPanResponderGrant`), the decay stops and `setOffset()` captures the current position. The newer Reanimated 2 library runs this entirely on the UI thread via "worklets," eliminating bridge latency for frame-accurate interruption.

The pattern is: start the coast animation immediately, interrupt it on new touch. This is exactly what our speculative snap-back does, adapted for overscroll recovery instead of content deceleration.

### Framer Motion and React Spring: cancel-and-restart is the native API

Both Framer Motion's `useSpring` hook and React Spring's imperative `api.start()` exhibit "from current" behavior by default. When a new animation target is set mid-flight, they read the current value and velocity from the running animation and use those as initial conditions for the new one. No explicit cancellation logic. No blending period. No state cleanup. The transition is C1-continuous (position and velocity both continuous at the switching instant) by construction.

This means animation interruption is architecturally trivial in these frameworks. Starting a speculative snap-back and then cancelling it on new input is the same operation as retargeting any spring — read current state, set new target. In our implementation, `cancelAnimationFrame` replaces the spring retarget, but the principle is identical.

### GSAP: the "overwrite" anti-pattern

GSAP (GreenSock Animation Platform) documents the exact anti-pattern we must avoid. Their default `overwrite: false` mode lets multiple tweens animate the same property simultaneously, causing them to "fight each other" — jittery, oscillating values. Their recommended `overwrite: "auto"` kills conflicting property animations, matching the guard-and-skip pattern described in our race condition defense (Section 5).

The double snap-back is our version of GSAP's overwrite problem: the speculative system calls `_snapBackElastic()`, then 80ms later the formal `onGestureEnd` calls it again. Two competing spring animations on the same elastic offset produce exactly the jitter GSAP warns about. Our defense ensures only one snap-back can run at a time.

## 5. The five-layer defense against race conditions {#race-condition-defense}

The most dangerous race condition in this phase is the **double snap-back**: the EWMA stall detector fires `_snapBackElastic()` speculatively, then the formal `TrackpadGestureDetector.onGestureEnd()` fires it again 50–150ms later. Without defense, two competing spring animations write to `elasticOffsetX/Y` on alternating frames, producing jitter, oscillation, and sometimes a visible glitch where the elastic offset jumps between two converging trajectories.

The defense strategy uses five layers, ordered from most architectural (prevents the problem) to most mechanical (catches it if earlier layers fail):

### Layer 1: Idempotent `_snapBackElastic` guard

The simplest and most effective defense. If the elastic animator is already running a snap-back animation, a new call to `_snapBackElastic()` with zero velocity is a no-op. The running animation continues undisturbed. This catches the exact scenario described above: speculative snap-back starts, formal gesture end fires, the guard rejects the second call.

The guard only applies to zero-velocity calls. If a new call arrives with nonzero velocity (from inertial coast termination), it should restart the spring with the new velocity, because the velocity contains important information about the user's gesture that would produce a more physically accurate animation. This distinction — skip zero-velocity duplicates, accept nonzero-velocity restarts — is the key design decision.

### Layer 2: State tracking via `_isSnappingBack` flag

A boolean flag `_isSnappingBack` is set to `true` when snap-back begins and `false` when it completes (animation settles) or is cancelled (user resumes input). This provides a semantic check that is independent of the elastic animator's internal `_rafId` state. Even if the animator's state is temporarily inconsistent (between a `cancel()` call and the next `requestAnimationFrame`), the flag provides a reliable source of truth.

### Layer 3: The cancel-before-restart pattern for new active input

When new input arrives (the user resumes scrolling), `_cancelSpeculativeSnapBack()` cancels any running snap-back animation before the input handler writes new elastic offset values. The cancellation reads the current animated value from the elastic animator and sets the elastic offset to that value, ensuring visual continuity. Then the input handler writes the new elastic offset based on the fresh overflow values, and the monitoring loop restarts to detect the next stall.

This pattern is the JavaScript equivalent of "current value, current velocity" handoff from animation frameworks. The critical detail: **read the animated value before cancelling, not after**. After cancellation, the animator's internal state is undefined.

### Layer 4: rAF as natural debounce

The monitoring loop runs via `requestAnimationFrame`, which guarantees at most one execution per frame. If both the speculative trigger and the formal trigger fire within the same 16ms frame, only the last one sees the current state. Since Layer 1's guard is checked inside `_snapBackElastic()`, the second call is rejected regardless of frame timing. But rAF provides an additional guarantee: the monitoring callback and the formal timeout callback cannot interleave within a single frame's execution.

Post-2019, the WHATWG spec guarantees that `cancelAnimationFrame` works correctly even within the same frame. If callbacks A and B are both scheduled for Frame N, and A runs first and cancels B, B will not run. This was inconsistent before 2019 (Firefox Bug 1509466), but is now reliable across all modern browsers.

### Layer 5: Diagnostic logging in development

In development mode, every state transition is logged with a `performance.now()` timestamp, the trigger source (`ewma_stall`, `formal_gesture_end`, `input_resumed`, `animation_complete`), the current elastic offset magnitude, and whether the elastic animator is running. This log makes timing-dependent bugs reproducible. If a double snap-back somehow fires despite Layers 1–4, the log reveals the exact sequence of events, the timing gap between the two triggers, and which layer's check failed.

### The trickiest scenario, traced through all layers

Consider this sequence:

```
t=0ms:    User scrolls past boundary. Elastic offset grows. EWMA monitoring starts.
t=100ms:  User lifts fingers. Momentum events begin (decaying deltas).
t=140ms:  EWMA drops below stall threshold. Speculative snap-back starts.
          → _isSnappingBack = true
          → elastic animator begins animating toward zero
t=170ms:  User resumes scrolling (touches trackpad again).
          → _cancelSpeculativeSnapBack() fires
          → Reads current animated elastic offset (say, 38px — partially decayed from 50px)
          → Sets elasticOffsetX = 38px (visual continuity)
          → Cancels elastic animator
          → _isSnappingBack = false
          → EWMA reinitialized to 10 (warm-up prevents immediate re-trigger)
t=170ms+: _feedElasticOverflow resumes writing new values.
          → EWMA monitoring restarts, watching for next stall.
t=350ms:  User lifts fingers again (for real this time).
t=460ms:  EWMA drops below threshold. Speculative snap-back starts (again).
          → _isSnappingBack = true
t=500ms:  Formal onGestureEnd fires (TrackpadGestureDetector timeout).
          → Calls _snapBackElastic({vx: 0, vy: 0})
          → Layer 1 guard: elastic animator is already running AND velocity is zero
          → No-op. Running animation continues.
t=700ms:  Elastic offset settles to zero.
          → _isSnappingBack = false
          → Animation complete.
```

Every transition is clean. No double snap-back. No visual discontinuity. The speculative system handles the visual response, and the formal system handles state management, exactly as designed.

## 6. Improved momentum detection constants in TrackpadGestureDetector {#momentum-detection}

### Why tighten the constants

The current `TrackpadGestureDetector` uses conservative constants that were appropriate when momentum detection directly gated the snap-back animation. With speculative snap-back handling the visual response, the formal detector's role changes from "gatekeeper" to "confirmer." False positives (detecting momentum too early) are now cheap: the speculative system has already started the snap-back, and a premature momentum detection simply advances the state machine slightly ahead of where it would otherwise be. This means we can safely tighten the constants to reduce detection latency without increasing user-visible errors.

### The constant changes

```javascript
// ===== BEFORE (current values) =====
const DECAY_STREAK_THRESHOLD = 3;       // 3 consecutive decaying deltas
const MIN_EVENTS_FOR_MOMENTUM = 6;      // At least 6 events before momentum
const TIMEOUT_ACTIVE_MS = 150;          // 150ms silence ends ACTIVE state
const TIMEOUT_MOMENTUM_MS = 100;        // 100ms silence ends MOMENTUM state

// ===== AFTER (Phase S3 values) =====
const DECAY_STREAK_THRESHOLD = 2;       // 2 consecutive decays (was 3)
const MIN_EVENTS_FOR_MOMENTUM = 4;      // 4 events minimum (was 6)
const TIMEOUT_ACTIVE_MS = 80;           // 80ms silence (was 150ms)
const TIMEOUT_MOMENTUM_MS = 60;         // 60ms momentum silence (was 100ms)
```

### Why each change is safe

**`DECAY_STREAK_THRESHOLD`: 3 → 2.** Two consecutive decaying deltas is still a strong momentum signal (the probability of two consecutive random deltas both being smaller than the previous is `~0.25` for uniform distributions, so this test rejects ~75% of active scrolling). With speculative snap-back already handling the visual response, a false-positive momentum detection is nearly invisible — it slightly changes the rubber-band coefficient from 0.55 to 0.3, which the user will not notice because the snap-back animation has already started.

**`MIN_EVENTS_FOR_MOMENTUM`: 6 → 4.** Four events at 60Hz is ~67ms of scrolling. This is still enough to establish a clear gesture pattern. The old threshold of 6 events (~100ms) was needed because momentum detection gated the snap-back. With speculation, the 6-event minimum only delayed the state transition without affecting the visual response.

**`TIMEOUT_ACTIVE_MS`: 150 → 80.** The active timeout fires `onGestureEnd` if no wheel events arrive for this duration during the ACTIVE state (the detector skipped MOMENTUM entirely — the gesture ended without momentum). The old 150ms was generous to avoid cutting off slow trackpad scrolling. At 80ms, the timeout is still longer than any reasonable inter-event gap during active trackpad scrolling (which produces events every 8–16ms at display refresh rate). Even the slowest deliberate trackpad movement produces events at <50ms intervals. 80ms comfortably captures the gap.

If this timeout fires prematurely (the user paused for 80ms during a scroll), the speculative snap-back has already started a gentle animation. When the user resumes, the snap-back is cancelled and input tracking resumes. The premature timeout advances the state machine to IDLE, triggering a new `onGestureStart` on the next wheel event, which correctly re-initializes the gesture state. The net effect of a false timeout is one extra `onGestureStart` → `onGestureEnd` cycle that the user never sees.

**`TIMEOUT_MOMENTUM_MS`: 100 → 60.** The momentum timeout fires `onGestureEnd` during MOMENTUM state when events stop arriving (momentum has fully decelerated). macOS momentum events arrive at display refresh rate (8–16ms apart) until they stop. A 60ms gap is ~4 missed frames at 60Hz, which is strong evidence that momentum has ended. The old 100ms was ~6 missed frames, unnecessarily conservative.

## 7. Complete annotated implementation: EWMA stall detector and speculative launcher {#speculative-impl}

### New properties in the Camera constructor

Add these properties to the Camera constructor in `vtt/js/map-camera.js`, in the Phase 6 initialization block alongside the existing `elasticOffsetX/Y` and `_cumulativeOverflowX/Y` declarations:

```javascript
    // Phase S3: Speculative snap-back
    //
    // The EWMA tracks the rate of change of elastic offset magnitude
    // in screen-space pixels per frame. When it drops below the stall
    // threshold, the speculative snap-back starts. When new input arrives,
    // it is cancelled. This eliminates the 1-2 second freeze between
    // gesture end and snap-back start.
    //
    // _elasticEWMA: The smoothed speed value. Initialized high (10) to
    //   prevent false positives during the first few frames of overscroll.
    //   Updated every frame by _checkSpeculativeSnapBack().
    //
    // _lastElasticScreenMag: The previous frame's elastic offset magnitude
    //   in screen-space pixels. Used to compute per-frame speed.
    //
    // _speculativeSnapId: The rAF ID for the monitoring loop. Not null
    //   means the monitoring loop is running. We use null as the sentinel
    //   (not 0) because MDN warns that rAF IDs are per-window incrementing
    //   counters that may wrap to 0.
    //
    // _isSnappingBack: Layer 2 defense flag. True when snap-back animation
    //   is in progress (speculative or formal). Prevents double snap-back.
    this._elasticEWMA = 0;
    this._lastElasticScreenMag = 0;
    this._speculativeSnapId = null;
    this._isSnappingBack = false;
```

### The `_checkSpeculativeSnapBack()` method

This method runs on every animation frame when elastic offset is nonzero. It computes the EWMA, checks the stall condition, and launches snap-back when appropriate.

Add this to the Camera class in `vtt/js/map-camera.js`, near the other elastic offset methods (`_feedElasticOverflow`, `_snapBackElastic`):

```javascript
  // -------------------------------------------------------
  // Phase S3: Speculative snap-back monitoring
  // -------------------------------------------------------

  /**
   * EWMA stall detection and speculative snap-back launcher.
   *
   * Runs once per animation frame when elastic offset is nonzero.
   * Computes the exponentially weighted moving average (EWMA) of
   * elastic offset change rate in screen-space pixels per frame.
   * When the EWMA drops below the stall threshold, starts a gentle
   * snap-back animation. If new input arrives, _feedElasticOverflow()
   * cancels the snap-back and resumes following the gesture.
   *
   * The EWMA uses α = 0.3, giving an effective memory of ~5.7 frames
   * (~95ms at 60Hz) and detection latency of ~108ms from typical
   * scrolling speed. This is within Google's RAIL 100ms budget when
   * combined with the speculative animation's first-frame response.
   *
   * The stall threshold is in screen pixels per frame, making it
   * zoom-independent. At high zoom, small world-space movements produce
   * large screen-space movements, so the threshold naturally requires
   * more deceleration before triggering. At low zoom, the same
   * world-space movement produces tiny screen-space movement, and
   * the threshold triggers appropriately.
   */
  _checkSpeculativeSnapBack() {
    // -------------------------------------------------------
    // Step 1: Compute per-frame speed in screen space
    // -------------------------------------------------------
    // Screen magnitude = world magnitude × zoom. This makes the
    // speed measurement perceptually correct at all zoom levels.
    const currentScreenMag = Math.sqrt(
      (this.elasticOffsetX * this.zoom) ** 2 +
      (this.elasticOffsetY * this.zoom) ** 2
    );
    const delta = Math.abs(currentScreenMag - this._lastElasticScreenMag);
    this._lastElasticScreenMag = currentScreenMag;

    // -------------------------------------------------------
    // Step 2: Update EWMA
    // -------------------------------------------------------
    // α = 0.3: responds within ~6.5 frames of sustained zero-speed.
    // S_t = α · |delta| + (1 − α) · S_{t-1}
    const EWMA_ALPHA = 0.3;
    this._elasticEWMA = EWMA_ALPHA * delta + (1 - EWMA_ALPHA) * this._elasticEWMA;

    // -------------------------------------------------------
    // Step 3: Check stall condition
    // -------------------------------------------------------
    // Stall = elastic offset exists AND is barely changing in screen space.
    //
    // STALL_THRESHOLD: 0.5 screen pixels per frame. Below human visual
    // threshold for movement detection (~1 arcminute at typical viewing
    // distance). Values below this are perceptually frozen.
    //
    // MIN_MAGNITUDE: 1.0 screen pixel. Don't trigger snap-back for
    // sub-pixel elastic offsets; they will be cleaned up by the settle
    // check in the elastic animator.
    const STALL_THRESHOLD = 0.5;  // screen px per frame
    const MIN_MAGNITUDE = 1.0;    // screen px

    if (currentScreenMag > MIN_MAGNITUDE && this._elasticEWMA < STALL_THRESHOLD) {
      // Stall detected. Start snap-back if not already running.
      if (!this._isSnappingBack) {
        this._snapBackElastic();
      }
    }

    // -------------------------------------------------------
    // Step 4: Continue monitoring or stop
    // -------------------------------------------------------
    // Keep the monitoring loop running while elastic offset is visible.
    // When the magnitude drops to zero (snap-back completed or offset
    // was manually zeroed), stop monitoring. This allows the browser
    // to enter idle state between interactions, preserving battery.
    //
    // The 0.5 threshold here matches SETTLE_THRESHOLD_PX: the same
    // threshold the spring solver uses to decide "close enough to zero."
    if (currentScreenMag > 0.5) {
      this._speculativeSnapId = requestAnimationFrame(
        () => this._checkSpeculativeSnapBack()
      );
    } else {
      this._speculativeSnapId = null;
    }
  }

  /**
   * Cancel the speculative snap-back monitoring loop and any running
   * snap-back animation. Called when new active input arrives (the user
   * resumed scrolling) or when the gesture system needs to take over.
   *
   * If a snap-back animation is running, reads the current animated
   * elastic offset and preserves it (Layer 3: value handoff). This
   * ensures visual continuity — the elastic offset jumps to wherever
   * the animation had reached, not back to the pre-animation value.
   */
  _cancelSpeculativeSnapBack() {
    // Stop the monitoring loop
    if (this._speculativeSnapId != null) {
      cancelAnimationFrame(this._speculativeSnapId);
      this._speculativeSnapId = null;
    }

    // Cancel any running snap-back animation with value handoff
    if (this._isSnappingBack && this._elasticAnimator) {
      // Layer 3: Read current animated position before cancelling.
      // The elastic animator's _tick writes to elasticOffsetX/Y every
      // frame, so the current values already reflect the latest animation
      // state. We just need to ensure the animator does not write stale
      // values after we cancel it.
      this._elasticAnimator.cancel();
      this._isSnappingBack = false;
      // elasticOffsetX/Y retain whatever value the last _tick wrote.
      // This is the value handoff — visual continuity is preserved.
    }
  }
```

### Why the monitoring loop uses its own rAF

The speculative system uses its own `requestAnimationFrame` loop (`_speculativeSnapId`) rather than piggybacking on the elastic animator's rAF or a global render loop. There are three reasons:

**Independence from the elastic animator.** The monitoring loop must run when the elastic animator is *not* running (during active scrolling, before any snap-back has started). If monitoring depended on the elastic animator's rAF, it would only check during snap-back, which defeats the purpose.

**Self-terminating behavior.** The monitoring loop starts when elastic offset becomes nonzero and stops when it reaches zero. Between interactions, no rAF callbacks are scheduled. This is critical for battery life: Cytoscape.js documented that a persistent rAF loop prevents the browser from entering idle state, causing measurable battery drain on mobile devices. Our loop starts only when needed and stops immediately when done.

**Clear cancellation semantics.** `cancelAnimationFrame(this._speculativeSnapId)` cancels exactly one callback. There is no ambiguity about what is being cancelled. If we shared a rAF with other systems, cancellation would require flag-based conditional logic inside the callback, adding complexity and potential for bugs.

## 8. Complete annotated implementation: modified `_feedElasticOverflow` {#feed-overflow-impl}

The `_feedElasticOverflow()` method is the entry point for all elastic offset updates. It must be modified to:

1. Cancel any running speculative snap-back when new input arrives (the user is still scrolling).
2. Start the monitoring loop when elastic offset first becomes nonzero.
3. Reinitialize the EWMA to prevent immediate re-triggering after cancellation.

Replace the existing `_feedElasticOverflow()` method in `vtt/js/map-camera.js`:

```javascript
  /**
   * Feed overflow (distance past hard bounds) into the elastic offset.
   * The rubber-band formula operates in screen-space pixels for consistent
   * resistance feel, then converts back to world-space for the offset.
   *
   * Phase S3 additions:
   *   - Cancels speculative snap-back on new input (user is still scrolling)
   *   - Starts the EWMA monitoring loop when elastic offset first appears
   *   - Reinitializes EWMA to prevent immediate re-triggering
   */
  _feedElasticOverflow(overflowX, overflowY) {
    if (!this._gestureActive) return;

    // -------------------------------------------------------
    // Phase S3: Cancel any speculative snap-back.
    // -------------------------------------------------------
    // The user is still providing active input. If a speculative
    // snap-back is running (the EWMA briefly dropped below threshold
    // during a pause in scrolling), cancel it immediately and resume
    // following the input. The cancel preserves visual continuity
    // (Layer 3: the elastic offset retains the animation's current value).
    if (this._isSnappingBack) {
      this._cancelSpeculativeSnapBack();
    }

    // Dampen rubber-band during trackpad momentum (c=0.3 vs 0.55)
    const c = this._momentumScrollActive ? 0.3 : 0.55;

    if (overflowX !== 0) {
      const screenOverflow = overflowX * this.zoom;
      const dampened = rubberBand(Math.abs(screenOverflow), this.viewportW, c);
      this.elasticOffsetX = Math.sign(overflowX) * dampened / this.zoom;
    } else {
      this.elasticOffsetX = 0;
    }

    if (overflowY !== 0) {
      const screenOverflow = overflowY * this.zoom;
      const dampened = rubberBand(Math.abs(screenOverflow), this.viewportH, c);
      this.elasticOffsetY = Math.sign(overflowY) * dampened / this.zoom;
    } else {
      this.elasticOffsetY = 0;
    }

    // -------------------------------------------------------
    // Phase S3: Start monitoring loop if not already running.
    // -------------------------------------------------------
    // The monitoring loop checks the EWMA every frame and launches
    // speculative snap-back when the rate of change stalls. We start
    // it here (on new overflow input) and it self-terminates when
    // elastic offset returns to zero.
    //
    // The EWMA is initialized high (10) to prevent immediate
    // triggering. With α = 0.3, it takes ~140ms of sustained
    // zero-speed to decay below the 0.5 threshold. This warm-up
    // prevents false positives during the first frames of overscroll.
    if (this._speculativeSnapId == null &&
        (this.elasticOffsetX !== 0 || this.elasticOffsetY !== 0)) {
      this._lastElasticScreenMag = Math.sqrt(
        (this.elasticOffsetX * this.zoom) ** 2 +
        (this.elasticOffsetY * this.zoom) ** 2
      );
      this._elasticEWMA = 10;  // Anti-FIR: start high to prevent premature trigger
      this._speculativeSnapId = requestAnimationFrame(
        () => this._checkSpeculativeSnapBack()
      );
    }
  }
```

### What changed from the original

The original `_feedElasticOverflow()` had no awareness of the speculative system. The Phase S3 version adds three things:

1. **`_cancelSpeculativeSnapBack()` call at the top.** This is the "new input cancels speculation" mechanism. Without this, a speculative snap-back would continue running while new overflow values are being written, causing the elastic offset to jump between the animation's trajectory and the overflow-driven values on alternating frames.

2. **Monitoring loop startup at the bottom.** The `if (this._speculativeSnapId == null)` check ensures the loop starts exactly once when elastic offset first appears. Subsequent calls to `_feedElasticOverflow()` see that the loop is already running and skip the initialization.

3. **EWMA reinitialization.** Setting `this._elasticEWMA = 10` on each monitoring startup prevents the EWMA from carrying over a stale low value from a previous interaction. If the user scrolls past the boundary, the EWMA decays to trigger snap-back, the snap-back completes, and then the user scrolls past the boundary again, the EWMA should start fresh from its high initial value, not from the near-zero value it had when the previous snap-back triggered.

## 9. Complete annotated implementation: `_snapBackElastic` double-fire guard {#snapback-guard-impl}

The `_snapBackElastic()` method is modified to prevent double snap-back and to maintain the `_isSnappingBack` flag. This is Layer 1 of the race condition defense.

Replace the existing `_snapBackElastic()` method in `vtt/js/map-camera.js`. Note: if Phase S2 has already been applied, this method already contains the velocity clamping logic. The Phase S3 changes add the double-fire guard around the existing S2 code:

```javascript
  /**
   * Trigger spring snap-back from current elastic offset to zero.
   * Uses the elastic animator (stiffness=400, omega~20) for snappier feel.
   *
   * Velocity is clamped to prevent spring overshoot (Phase S2).
   * Double-fire is prevented by the _isSnappingBack guard (Phase S3).
   *
   * This method is called from four places:
   *   1. TrackpadGestureDetector's onGestureEnd callback (zero velocity)
   *   2. _startInertialCoast termination (residual coast velocity)
   *   3. _cancelPan on blur/mouseleave (zero velocity)
   *   4. _checkSpeculativeSnapBack (zero velocity) [NEW in Phase S3]
   *
   * The double-fire guard (Layer 1):
   *   - If the elastic animator is already running AND the new velocity
   *     is zero, skip the call. The existing animation is at least as
   *     good as a zero-velocity restart (it may have started with real
   *     velocity from inertial coast).
   *   - If the new velocity is nonzero (from inertial coast), allow the
   *     restart. The new velocity contains gesture information that
   *     produces a more physically accurate animation.
   *
   * @param {{ vx: number, vy: number }} velocity  Initial velocity in
   *        world-space px/s. Defaults to zero.
   */
  _snapBackElastic(velocity = { vx: 0, vy: 0 }) {
    this._cumulativeOverflowX = 0;
    this._cumulativeOverflowY = 0;

    // -------------------------------------------------------
    // Phase S3 Layer 1: Double-fire guard
    // -------------------------------------------------------
    // If a snap-back is already running and the new call has zero
    // velocity, let the running animation continue. This prevents
    // the double snap-back from speculative + formal triggers.
    //
    // The check: velocity is zero AND the elastic animator is currently
    // animating (has an active rAF). We check both conditions because:
    //   - velocity.vx === 0 && velocity.vy === 0: the new call has no
    //     additional information (it would restart the spring with zero
    //     velocity, which is worse than the running animation's current
    //     velocity)
    //   - this._isSnappingBack: a snap-back is actually in progress
    //
    // If the new call has nonzero velocity (from inertial coast), we
    // let it through. The velocity clamp (S2) handles safety.
    const hasVelocity = velocity.vx !== 0 || velocity.vy !== 0;
    if (this._isSnappingBack && !hasVelocity) {
      return;  // Let the running animation continue
    }

    // Early return: if elastic offset is negligible, snap to zero
    if (Math.abs(this.elasticOffsetX) < 0.5 && Math.abs(this.elasticOffsetY) < 0.5) {
      this.elasticOffsetX = 0;
      this.elasticOffsetY = 0;
      this._isSnappingBack = false;
      EventBus.emit('camera:changed');
      return;
    }

    if (this._elasticAnimator) {
      const omega = this._elasticAnimator._omega;

      // Phase S2 Layer 1: Velocity clamping
      const clampedVx = this._clampSpringVelocity(
        velocity.vx, this.elasticOffsetX, omega
      );
      const clampedVy = this._clampSpringVelocity(
        velocity.vy, this.elasticOffsetY, omega
      );

      // Set the flag BEFORE starting the animation.
      // This ensures that any immediate re-entrant call (however unlikely)
      // sees the flag as true and hits the guard.
      this._isSnappingBack = true;

      this._elasticAnimator.snapBack(
        { x: this.elasticOffsetX, y: this.elasticOffsetY },
        { x: 0, y: 0 },
        { vx: clampedVx, vy: clampedVy }
      );
    }
  }
```

## 10. Complete annotated implementation: elastic animator value handoff on interruption {#value-handoff-impl}

The elastic animator's custom `_tick` function (created in `attachTo()`) must be updated to:

1. Clear `_isSnappingBack` when the animation completes.
2. Ensure the `_isSnappingBack` flag is properly managed throughout the animation lifecycle.

Update the elastic animator `_tick` in `attachTo()`. If Phase S2's position clamping has already been applied, integrate the S3 changes alongside the S2 code:

```javascript
    // Phase 6 + S2 + S3: elastic offset animator (stiffness=400).
    // Its _tick updates elasticOffsetX/Y instead of camera.x/y.
    this._elasticAnimator = new CameraAnimator(this, { stiffness: 400 });
    this._elasticAnimator._tick = ((cam) => {
      const anim = cam._elasticAnimator;
      return (timestamp) => {
        if (!anim._startTime) anim._startTime = timestamp;
        const elapsed = Math.min((timestamp - anim._startTime) / 1000, 2.0);
        const rx = anim._resolveAxis(anim._springX, elapsed);
        const ry = anim._resolveAxis(anim._springY, elapsed);

        // Phase S2 Layer 2: Position clamping (secondary overshoot defense)
        let valX = rx.value;
        let valY = ry.value;

        if (anim._springX) {
          if (anim._springX.displacement > 0 && valX < 0) {
            valX = 0;
          } else if (anim._springX.displacement < 0 && valX > 0) {
            valX = 0;
          }
        }

        if (anim._springY) {
          if (anim._springY.displacement > 0 && valY < 0) {
            valY = 0;
          } else if (anim._springY.displacement < 0 && valY > 0) {
            valY = 0;
          }
        }

        cam.elasticOffsetX = valX;
        cam.elasticOffsetY = valY;
        EventBus.emit('camera:changed');

        if (rx.settled && ry.settled) {
          cam.elasticOffsetX = 0;
          cam.elasticOffsetY = 0;
          cam._cumulativeOverflowX = 0;
          cam._cumulativeOverflowY = 0;

          // Phase S3: Clear snap-back flag on completion
          cam._isSnappingBack = false;

          EventBus.emit('camera:changed');
          anim.cancel();
          if (cam._gestures) cam._gestures.release('SNAP_BACK');
        } else {
          anim._rafId = requestAnimationFrame(anim._tick);
        }
      };
    })(this);
```

### What changed from the S2 version

The only addition is `cam._isSnappingBack = false` in the settled block. This clears the Layer 2 defense flag when the snap-back animation naturally completes, allowing future calls to `_snapBackElastic()` to proceed normally.

The `_isSnappingBack` flag is managed in three places:

| Operation | Sets flag to | Location |
|---|---|---|
| `_snapBackElastic()` starts animation | `true` | `_snapBackElastic()` body |
| Elastic animator settles | `false` | `_tick` settled block |
| `_cancelSpeculativeSnapBack()` cancels | `false` | `_cancelSpeculativeSnapBack()` body |

These three transitions form a complete lifecycle: `false → true (snap-back starts) → false (snap-back completes or is cancelled)`. There is no state where the flag can get stuck at `true` because every path that sets it to `true` has a corresponding path that sets it back to `false`.

## 11. Screen-space vs. world-space thresholds and zoom adaptation {#screen-vs-world}

### The zoom problem

The VTT's camera operates in world space. `elasticOffsetX` and `elasticOffsetY` are in world pixels. But the user perceives screen pixels. At zoom level 2.0, one world pixel is two screen pixels. At zoom level 0.5, one world pixel is half a screen pixel.

This distinction matters for three thresholds in the speculative system:

| Threshold | Value | Unit | Why this unit |
|---|---|---|---|
| EWMA stall threshold | 0.5 | Screen px/frame | Perceptual: "is the rubber-band visibly moving?" |
| EWMA minimum magnitude | 1.0 | Screen px | Perceptual: "is the rubber-band visible at all?" |
| Monitoring stop threshold | 0.5 | Screen px | Same as SETTLE_THRESHOLD_PX but in screen space |

All three thresholds are evaluated in screen space by multiplying world-space elastic offset by the current zoom level. This means:

- **At high zoom (e.g., 4.0):** A world-space elastic offset of 0.25px is 1.0 screen pixel — visible, and the monitoring continues. The EWMA stall threshold corresponds to 0.125 world px/frame of change.
- **At low zoom (e.g., 0.25):** A world-space elastic offset of 4.0px is 1.0 screen pixel — barely visible, and the monitoring continues. The EWMA stall threshold corresponds to 2.0 world px/frame of change.

This zoom adaptation is automatic. No conditional logic or threshold adjustments are needed. The single `* this.zoom` multiplication in the screen magnitude calculation handles everything.

### Comparison with the elastic animator's settle thresholds

The elastic animator uses `SETTLE_THRESHOLD_PX = 0.5` and `SETTLE_THRESHOLD_VEL = 0.5` in world space. This is slightly inconsistent with the speculative system's screen-space thresholds, but the inconsistency is harmless because the two systems serve different purposes:

- The elastic animator's thresholds determine when to stop the spring animation (at which point the elastic offset is snapped to exactly zero). These thresholds are in world space because the animator operates on world-space values.
- The speculative system's thresholds determine when to start the spring animation. These thresholds are in screen space because the decision is perceptual.

At normal zoom levels (0.5 to 3.0), the difference between 0.5 world pixels and 0.5 screen pixels is a factor of the zoom level — between 0.25 and 1.5 screen pixels. This is well below the 1-pixel perceptual threshold and has no visible effect.

## 12. The monitoring lifecycle: start, run, cancel, and battery impact {#monitoring-lifecycle}

### When does the monitoring loop start?

The monitoring loop starts in `_feedElasticOverflow()` when two conditions are met simultaneously:

1. `this._speculativeSnapId == null` — no monitoring loop is currently running.
2. Either `this.elasticOffsetX !== 0` or `this.elasticOffsetY !== 0` — there is visible elastic offset to monitor.

This means monitoring starts the first time the user scrolls past a map boundary in a given interaction. If the user scrolls within the map's bounds, no overflow occurs, no elastic offset is generated, and no monitoring starts.

### When does the monitoring loop run?

Once started, the monitoring loop runs once per animation frame (via `requestAnimationFrame`). Each frame, it:

1. Computes the current elastic offset magnitude in screen space.
2. Computes the per-frame change (delta) from the previous magnitude.
3. Updates the EWMA with the new delta.
4. Checks the stall condition (EWMA < 0.5 and magnitude > 1.0).
5. If stalled and not already snapping back, starts snap-back.
6. If magnitude > 0.5, schedules the next frame; otherwise, stops.

### When does the monitoring loop cancel?

The monitoring loop is cancelled by `_cancelSpeculativeSnapBack()` in three scenarios:

1. **New input in `_feedElasticOverflow()`.** The user resumed scrolling. The monitoring loop is cancelled, the EWMA is reinitialized (on next `_feedElasticOverflow` call when it restarts), and the system follows the new input.
2. **A new gesture preempts via `GestureStateMachine`.** For example, the user starts a mouse drag while elastic offset is nonzero. The state machine's `_cancelCurrent()` method should call `_cancelSpeculativeSnapBack()` when cancelling `SNAP_BACK`.
3. **The elastic offset reaches zero.** The monitoring loop self-terminates (Step 4 in `_checkSpeculativeSnapBack()`: if magnitude ≤ 0.5, set `_speculativeSnapId = null` and do not schedule another frame).

### Battery impact

The Cytoscape.js project documented that a persistent `requestAnimationFrame` loop prevents the browser from entering idle state, causing measurable battery drain on mobile devices and laptops. Our monitoring loop avoids this problem by design:

- The loop only runs when elastic offset is nonzero (the user is scrolling past a boundary or the snap-back animation is in progress).
- It self-terminates when the elastic offset returns to zero.
- Between interactions, zero rAF callbacks are scheduled.

The per-frame cost of the monitoring loop is negligible: one `Math.sqrt`, two multiplications, one `Math.abs`, two floating-point comparisons, and one EWMA update. Total: approximately 0.02ms per frame, which is less than 0.1% of the 16.67ms frame budget.

## 13. Edge cases and what to watch out for {#watch-out}

### The EWMA alpha (0.3) is a tuning parameter

α = 0.3 is well-grounded in the math (Section 3), but real-world performance depends on hardware-specific factors: trackpad sensitivity, display refresh rate, and macOS momentum decay characteristics. If testing reveals that the speculative snap-back triggers too early (the user is still scrolling but the EWMA drops below threshold during a momentary pause), increase α to 0.25 or 0.2. If it triggers too late (the freeze is still perceptible), decrease α to 0.35 or 0.4. The range 0.2 to 0.4 is the viable window; values outside this range are either too sluggish or too twitchy.

### Zoom changes during elastic overscroll

If the user zooms while elastic offset is nonzero (possible via Ctrl+scroll or mouse wheel), the screen-space magnitude of the elastic offset changes instantly. A 50px world-space offset at zoom 1.0 is 50 screen pixels; at zoom 2.0, it is 100 screen pixels. This sudden change in screen magnitude produces a large per-frame delta in the EWMA, which can briefly push the EWMA above the stall threshold and delay speculative snap-back.

This is acceptable behavior. During a zoom operation, the elastic offset should not snap back (the user is actively interacting). The elevated EWMA naturally prevents premature triggering. When the zoom operation ends, the EWMA decays back to baseline and the stall detection proceeds normally.

### The monitoring loop and the elastic animator compete for the same values

The monitoring loop reads `elasticOffsetX/Y` to compute the EWMA. The elastic animator writes `elasticOffsetX/Y` on every frame. If both are running simultaneously (after speculative snap-back triggers), the monitoring loop sees the animator-driven elastic offset decaying toward zero. This causes the EWMA to show activity (the offset is changing), which could theoretically prevent the monitoring loop from re-triggering snap-back.

This is fine. Once snap-back is running, we don't *want* re-triggering. The monitoring loop's job is to detect stalls during the period *before* snap-back starts. Once the elastic animator is running, the snap-back is in progress and the monitoring loop's EWMA value is irrelevant. The monitoring loop continues running (because magnitude > 0.5) but its stall check is blocked by `if (!this._isSnappingBack)`, so it never triggers a second snap-back.

### The formal `onGestureEnd` fires while speculative snap-back is running

This is the primary double snap-back scenario. The defense is straightforward:

1. `onGestureEnd` callback calls `_snapBackElastic({ vx: 0, vy: 0 })`.
2. Inside `_snapBackElastic`, the Layer 1 guard checks: `this._isSnappingBack === true` and `velocity.vx === 0 && velocity.vy === 0`.
3. Both conditions are met. The method returns immediately.
4. The running speculative animation continues undisturbed.

### The formal `onGestureEnd` fires *before* speculative snap-back triggers

This happens when the formal detector is faster than the EWMA (which is possible for gestures with clear momentum decay patterns that are detected quickly). In this case, `onGestureEnd` fires with `_isSnappingBack === false`, so the Layer 1 guard allows the call through. `_snapBackElastic()` starts the spring normally. The monitoring loop sees `_isSnappingBack === true` on its next frame and does not trigger a second snap-back. Everything works correctly.

### `_startInertialCoast()` and the monitoring loop

Inertial coast (from mouse drag release) uses `panBy()`, which calls `_feedElasticOverflow()`. Each `_feedElasticOverflow()` call cancels any running speculative snap-back (because new input is arriving). This means the speculative system is effectively disabled during inertial coast. When the coast ends (velocity drops below `STOP_THRESHOLD`), `_snapBackElastic()` is called with the residual coast velocity. At this point, the monitoring loop has been cancelled (by repeated `_feedElasticOverflow` calls) and will be restarted only if the snap-back produces new elastic offset changes.

This is correct behavior. During inertial coast, the elastic offset is being driven by the coast's `panBy()` calls, and the coast has its own termination logic. The speculative system should not interfere.

### Tab backgrounding and `_startTime` drift

If the user backgrounds the tab while elastic offset is nonzero, `requestAnimationFrame` callbacks stop firing. When the tab is foregrounded, the monitoring loop's next callback receives a large timestamp jump. The EWMA's `delta` will be computed from the difference between the current (large) screen magnitude and the stale `_lastElasticScreenMag`. If the elastic offset has not changed (it shouldn't, since no events were processed while backgrounded), the delta will be zero, and the EWMA will decay toward zero from its pre-backgrounding value. This will likely trigger the stall condition, which is correct — the elastic offset has been frozen for the entire time the tab was backgrounded, and snap-back should start immediately.

The elastic animator has its own protection against tab backgrounding: its `_tick` function clamps elapsed time to 2.0 seconds, preventing the spring from jumping to its settled state in a single frame. This means the snap-back animation plays out normally (with at most 2 seconds of "time skipped") when the tab is foregrounded.

## 14. Testing protocols {#testing}

### Unit tests

All unit tests run inside `page.evaluate()` in Playwright, importing modules directly. They test mathematical correctness without timing dependencies. Add these to a new file `tests/speculative-snapback.spec.js` or add to the existing `tests/phase6-unit.spec.js`.


#### Test 2: EWMA does not trigger during sustained high-speed input

```javascript
test('EWMA stays above threshold during constant-speed elastic growth', async ({ page }) => {

    for (let i = 0; i < 30; i++) {
```

### Manual testing checklist

Because the speculative snap-back system is deeply tied to real-world trackpad behavior, timing, and human perception that cannot be perfectly simulated with `dispatchEvent`, manual testing is essential.

1. **Slow two-finger scroll past map edge:** Camera pans to boundary, elastic rubber-band appears, finger lift triggers snap-back. Snap-back should begin almost immediately (within ~100ms), not after a visible freeze. This is the primary test case for Phase S3.

2. **Fast two-finger swipe past map edge (THE CRITICAL TEST):** Swipe fast with two fingers past the boundary. The rubber-band should stretch, and snap-back should begin within ~100ms of fingers lifting. There must be NO visible freeze between the rubber-band reaching maximum stretch and the snap-back animation starting. Repeat 10+ times at varying speeds.

3. **Slow scroll past boundary, pause mid-gesture, resume scrolling:** Scroll past the boundary, pause for 200ms (do not lift fingers), then resume scrolling. The elastic offset should remain visible during the pause (the speculative snap-back should not trigger because fingers are still on the trackpad). When scrolling resumes, the elastic offset should follow the new input smoothly.

4. **Fast scroll past boundary, immediately scroll back:** Swipe past the boundary, then immediately swipe back (without lifting fingers). The elastic offset should smoothly reduce as the user scrolls back. If speculative snap-back briefly triggered during the direction change, it should be cancelled seamlessly with no visible glitch.

5. **Right-click drag past boundary, fast release:** This tests the interaction between inertial coast and speculative snap-back. The coast should push into the elastic zone, then snap-back should begin without freezing.

6. **Sustained scroll at boundary (maximum overscroll):** Hold two fingers on the trackpad and continuously scroll past the boundary for 3+ seconds. The elastic offset should reach its rubber-band-limited maximum and stay stable. Speculative snap-back should NOT trigger during sustained scrolling (the EWMA should stay above threshold).

7. **Pinch-to-zoom during elastic overscroll:** While elastic offset is visible, perform a pinch-to-zoom gesture. The zoom should work correctly. The elastic offset should persist during zoom (zoom does not cancel elastic). After the zoom, the elastic offset should snap back normally.

8. **Open Controller and Display (cross-window):** Perform all the above tests with the VTT Display open. Elastic effects should be local-only (elastic offset is not synced across windows). The Display should see the camera position settle to the boundary smoothly.

## 15. Long-term tie-ins to future phases {#long-term}

### Phase S4 (Hierarchical gesture coordination with hysteresis)

Phase S4 restructures the `GestureStateMachine` with dwell time, cooldown, and hierarchical preemption rules. The speculative snap-back system must integrate with S4's `_cancelCurrent()` method. Specifically, when `_cancelCurrent()` cancels a `SNAP_BACK` gesture, it must call `_cancelSpeculativeSnapBack()` to stop both the monitoring loop and any running snap-back animation.

The current code in the overview shows:

```javascript
case 'SNAP_BACK':
  this._camera._cancelSpeculativeSnapBack();
  if (this._camera._elasticAnimator) this._camera._elasticAnimator.cancel();
  break;
```

With Phase S3 in place, `_cancelSpeculativeSnapBack()` already handles both the monitoring loop and the elastic animator cancellation, so the explicit `_elasticAnimator.cancel()` call is redundant. But keeping it as defense-in-depth is harmless.

S4's dwell time (80ms minimum before mode switching) and cooldown (50ms after gesture end) interact positively with Phase S3. The cooldown after `onGestureEnd` prevents a new gesture from starting during the first 50ms of snap-back, which reduces the chance of the snap-back being interrupted by noise. The dwell time prevents the gesture state machine from oscillating between SCROLL_PAN and SNAP_BACK during the transition period.

### Phase S5 (Unified spring physics and beyond-parity features)

Phase S5's long-term vision is a unified spring integrator per axis that replaces all three current animation systems. In this architecture, speculative snap-back becomes even simpler: instead of starting and cancelling a discrete animation, you just set the spring's target to zero. The spring continuously resolves toward its target, so setting the target to zero immediately starts the return animation. If new input arrives, setting the target back to the overscrolled position (or just letting `_feedElasticOverflow` write values directly) seamlessly interrupts the snap-back. No explicit cancellation, no `_isSnappingBack` flag, no monitoring loop. The spring's "current value, current velocity" behavior handles everything.

Until that unification happens, the explicit monitoring loop and state flag are necessary. But they are designed to be easy to remove: the monitoring loop is self-contained (one rAF callback), the state flag has three well-defined transitions, and the `_cancelSpeculativeSnapBack()` method encapsulates all cleanup.

Phase S5 also simplifies the overflow accumulation model (replacing the 0.8 decay with proportional input-correlated reduction). The speculative snap-back system does not depend on the specific overflow accumulation model — it monitors the result (elastic offset change rate), not the mechanism. Any change to how overflow translates to elastic offset is transparent to the EWMA.

### Phase 7 (Touch support via PointerEvent)

Touch gestures on mobile devices have a different momentum model than macOS trackpad scrolling. On iOS, `UIPanGestureRecognizer` provides explicit velocity on gesture end, and the momentum deceleration is handled by the OS. On Android, touch momentum is typically implemented in JavaScript (or via `RecyclerView`'s built-in scroll physics).

The speculative snap-back system is device-agnostic. It monitors elastic offset change rate, not the input device. Whether the elastic offset is driven by trackpad wheel events, mouse drag, or touch pan, the EWMA detects stalls the same way. When Phase 7 adds touch support, the speculative system works out of the box — no modifications needed.

However, the EWMA alpha value may need tuning for touch. Touch gestures on mobile devices produce different velocity profiles: more abrupt stops (finger lifts cleanly off screen) with less momentum (shorter deceleration tails). This means the speed drops faster, and the EWMA detects the stall sooner. If testing reveals that touch users see snap-back starting too aggressively during active scrolling, consider a slightly lower alpha (0.25) for touch interactions.

### Phase 8 (Camera presets with spring transitions)

Camera presets (saved positions that the DM recalls during a session) use spring animations to transition from the current position to the preset. If the camera has elastic offset when a preset is recalled, the speculative snap-back should be cancelled (the preset transition takes priority), and the elastic offset should be zeroed immediately (the camera is jumping to a new position, not returning to the boundary).

This is a clean interaction: `_cancelSpeculativeSnapBack()` followed by explicit elastic offset zeroing. The preset's spring animation operates on camera position (`x`, `y`, `zoom`), not on elastic offset, so there is no conflict.

### Performance monitoring

The speculative snap-back system generates valuable telemetry data:

- **EWMA detection latency:** Time between the last significant elastic offset change and the speculative snap-back trigger. Target: < 150ms.
- **Misprediction rate:** How often the speculative snap-back is cancelled by new input within 100ms of triggering. Target: < 10%.
- **Formal vs. speculative timing:** How often the speculative trigger fires before the formal `onGestureEnd`, and the time gap between them. This measures how much latency the speculative system eliminates.
- **Monitoring loop duration:** Total frames the monitoring loop runs per interaction. This tracks battery impact.

These metrics can be logged to the diagnostic system added in Phase S3's Layer 5 defense. For now, `console.debug` is sufficient; production telemetry can be added when the VTT's monitoring infrastructure is built.
